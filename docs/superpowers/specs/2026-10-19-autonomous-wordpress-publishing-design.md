# 텔레그램 제휴 링크 기반 WordPress 자동 발행 설계

최종 수정: 2026-10-20
상태: 사용자 승인 완료 (2026-10-20, "ㄱㄱㄱ"), 구현 계획 작성 단계

## 1. 합의한 목표

사용자가 **본인 계정에서 발급한 쿠팡·토스 제휴 링크**를 텔레그램으로 보내면, 앱이 상품에 맞는 글을 작성하고 WordPress에 자동 발행한다. 상품 정보를 읽지 못할 때만 봇이 설명을 요청하며, 사용자가 답하면 자동 처리를 재개한다. 사용자는 이 보충 입력 흐름에 동의했다.

`제휴 링크 접수 → 상품 정보 확인 → 필요한 설명 보충 → 상황별 글 작성·검사 → 서비스별 일정에 맞춰 발행 → 텔레그램 결과 알림`

- 게시글의 구매 링크에는 전달받은 제휴 URL을 그대로 사용한다.
- 쿠팡·토스 API 설정 없이 동작한다. Telegram, 기존 AI 연결과 WordPress 연결을 사용한다.
- 초기 설정 후 글마다 적용·승인 버튼을 누르지 않는다.
- 쿠팡·토스의 하루 발행 편수는 각각 설정한다.
- 첫 구현 단위는 메시지 하나의 상품 링크 하나에 대한 글 한 편이다. 단일 상품 소개·구매 가이드·짧은 정보 글을 지원한다.

이 문서는 기존의 상품 API 자동 탐색 설계를 대체한다.

## 2. 조사 결과와 구현 접근

실제 쿠팡 제휴 링크를 확인해 상품·옵션 식별자가 포함된 최종 주소까지 도달했다. 현재 환경에서는 HTTP 요청과 Chrome 모두 상품 본문에 HTTP 403을 받았다. 별도 검색에서 상품명은 찾았으나 최신 가격·옵션 상세를 확인한 것은 아니다. 조사 도구의 웹 검색은 앱에 구현된 기능이 아니다. 사용자의 원문 제휴 링크·계정 추적 값은 설계와 테스트 자료에 복사하지 않는다.

### Telegram 수신 방식

| 접근 | 특징 |
| --- | --- |
| **앱에서 새 메시지를 가져오는 long polling (추천)** | PC/NAS에서 기존 앱과 함께 실행, 외부 수신 주소나 포트 개방 없이 사용 |
| Telegram webhook 수신 | 공개 HTTPS 주소와 외부 요청 인증·배포 설정 필요 |

기존 단일 프로세스와 SQLite에 맞춰 long polling과 내부 작업 실행기를 사용한다. 메시지 수신·상품 처리·알림 전달을 분리해 긴 상품 조회나 글 작성이 새 메시지 접수를 막지 않게 한다. 네트워크 요청 중에는 DB 잠금을 유지하지 않는다.

## 3. 사용자 경험

### 정상 처리

1. 개인 봇 대화에 제휴 링크를 보낸다. 링크와 함께 상품 설명을 보내도 된다.
2. 봇이 요청 번호와 쿠팡·토스 구분을 포함해 접수를 알린다.
3. 상품 정보가 충분하면 준비 대기열에 넣는다.
4. 설정한 서비스별 일정에 맞춰 글 작성·검사와 WordPress 예약을 진행한다.
5. 예약 확인 시 예정 시각을, 실제 공개 확인 시 글 제목·주소를 회신한다.

### 정보 보충

조회 실패 또는 정보 부족 시 봇이 요청 번호가 있는 질문을 보낸다. 사용자는 해당 메시지의 **답장**으로 필요한 내용을 보낸다.

```text
상품명: 상품 이름과 선택한 옵션
특징: 확인한 특징이나 구성
특징: 추가로 확인한 내용
가격: 선택 입력
대상: 선택 입력, 소개하고 싶은 독자
```

상품명과 적어도 하나의 구체적인 특징이 필요하다. 봇은 확보된 값은 유지하고 누락된 항목만 요청한다. 설명이 충분해지면 같은 작업을 자동 재개한다. 여러 상품이 정보 대기 중이어도 답장 대상의 요청에만 설명을 연결한다. 연결되지 않은 텍스트는 임의의 상품에 합치지 않고 답장 방법을 안내한다.

첫 버전의 보충 자료는 텍스트로 처리한다. 사진만 전달되면 상품명을 포함한 텍스트 설명을 요청한다. 입력 메시지의 사진 캡션에 링크나 텍스트 설명이 있으면 그 텍스트는 사용할 수 있다.

`/start`는 사용 방법, `/status`는 서비스별 대기·정보 요청·예약·발행 현황을 안내한다. 웹 화면에서도 같은 작업 기록을 확인한다.

## 4. 수신, 권한과 원문 링크 보존

- 서버 환경변수: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `TELEGRAM_ALLOWED_USER_ID`. 등록한 사용자의 개인 대화만 작업 입력으로 받는다.
- 메시지의 채팅·발신자 ID를 먼저 검사한 뒤 URL 처리와 외부 요청을 수행한다. 다른 사용자의 입력은 작업을 만들지 않는다.
- `getUpdates`의 메시지와 캡션에서 `url`·`text_link` 엔티티를 처리한다. Telegram의 UTF-16 오프셋을 지켜 한글·이모지가 포함된 메시지에서도 링크를 정확히 추출한다.
- 하나의 메시지에 서로 다른 지원 링크가 여러 개 있으면 각각 별도 메시지로 보내도록 안내한다. 동일 링크의 중복 표기는 하나로 처리한다.
- 지원 형태는 쿠팡의 `link.coupang.com`·`coupa.ng` 제휴 주소, 토스의 `toss.im/_m/` 및 추적 정보가 있는 `toss.shopping` 제휴 주소다. 실제 추가 형식은 해당 서비스 주소임을 검증한 뒤 확장한다.
- `affiliate_url`에는 엔티티에서 얻은 주소를 쿼리·추적 값 변경 없이 저장한다. 최종 상품 주소·상품 식별자는 별도 필드로 저장한다. HTML에서는 이스케이프만 하고 실제 링크 목적지는 유지한다.
- 계정 귀속은 사용자가 본인 링크라고 제공한 사실에 근거한다. API로 계정 소유권을 확인했다고 표시하지 않는다.
- 입력을 DB에 저장한 뒤에만 다음 `offset`으로 수신 확인한다. 봇 ID와 `update_id`, 채팅 ID와 `message_id`로 재수신을 식별한다. 무시한 업데이트도 확인 처리해 수신이 멈추지 않도록 한다.
- 메시지 수정 이벤트는 새 게시 요청으로 처리하지 않는다. 연결된 보충 답변만 준비 단계의 근거를 갱신한다.
- 다른 webhook이나 같은 토큰의 수신기와 충돌하면 연결 오류를 표시한다. Telegram 연결 설정은 앱 재시작 후 적용한다.

## 5. API 없는 상품 정보 확인

### 조회와 추출

- 허용한 쿠팡·토스 HTTPS 주소를 조회하고 리다이렉트를 최대 5회 따라간다. 최종 상품 URL에서 서비스·상품·옵션 식별자를 추출한다.
- 각 이동마다 목적지 호스트·포트·DNS 결과를 확인하고 검증한 공개 IP로 연결한다. 내부망·로컬 주소로의 이동은 허용하지 않는다. 인증정보나 브라우저 쿠키는 전달하지 않는다.
- 조회 체인 전체에 20초 제한을 두고, 각 응답의 압축 해제 후 본문을 최대 2MiB까지 읽는다. HTML에서 JSON-LD Product/Offer, Open Graph 및 명시적인 상품 메타데이터를 추출한다.
- 상품명·옵션·설명·가격 등 필드별로 출처와 수집 시각을 기록한다. 여러 상품이나 옵션이 섞여 대응을 확정할 수 없는 값은 사용하지 않는다.
- 페이지 문구와 사용자 설명은 작성 자료로 전달한다. 자료 안의 실행 지시나 임의의 외부 URL을 작업 명령으로 사용하지 않는다.

### 보충 입력으로 전환하는 조건

- HTTP 403, 로그인·접근 차단 화면, 앱 전용 이동, 지원하지 않는 리다이렉트, 추출 가능한 상품 정보 부족.
- 시간 초과·일시적 서버 오류는 지연 재시도 후 실패하면 정보 보충으로 전환한다.
- 상품명을 구별할 수 없거나 구체적인 특징이 없으면 `awaiting_info`로 저장하고 질문을 보낸다. 링크 ID만 보고 사양이나 사용 경험을 만들지 않는다.
- 사용자가 보낸 텍스트를 `사용자 제공` 근거로 기록한다. 페이지에서 확인한 정보와 충돌하면 해당 항목의 설명을 요청한다.
- 상품 페이지를 열 수 없더라도 유효한 제휴 URL과 충분한 사용자 설명이 있으면 글을 만들 수 있다. 이 경우 출처 표시는 사용자 제공 설명과 접수 시각에 맞춘다.
- 발행 전에 24시간이 지난 가격은 재확인하거나 글에서 제외한다. 가격이 없어도 다른 근거가 충분하면 자동 발행을 계속한다.

## 6. 상황별 프롬프트와 자동 검사

공통 지침, 카테고리별 추가 지침, 글 유형별 템플릿을 조합한다. 웹 설정에서 주제·독자·말투·추가 지침을 수정할 수 있으며, 사용한 버전은 작업에 저장한다.

| 자료 상황 | 작성 방식 |
| --- | --- |
| 상품명과 독립된 사실 3개 이상 | 단일 상품 소개, 목표 1,200~2,000자 이내 |
| 위 조건과 구체적인 구매 목적·대상 독자 | 구매 가이드, 해당 목적에 필요한 확인 항목 중심 |
| 상품명과 사실 1~2개 | 300~700자 이내 짧은 정보 글 |
| 상품명 또는 구체적 사실 부족 | 텔레그램 보충 입력 요청 |

사실 개수에는 상품명·URL·상품 ID·조회 시각·중복 문장을 포함하지 않는다. 구체적인 목적과 사실 3개 이상이 있으면 구매 가이드, 그다음 근거 양에 따른 소개·짧은 글 순서로 선택한다. 분량을 채우기 위해 근거를 늘리지 않는다.

카테고리는 명시적인 페이지 정보나 사용자 입력을 사용하고, 확인되지 않으면 일반 상품 템플릿을 적용한다. 예를 들어 생활용품은 구성·사용 전 확인 사항, 디지털 제품은 확인된 사양·호환성 항목을 중심으로 작성한다. 카테고리 이름만으로 제품 속성을 추정하지 않는다.

- 출력은 제목·제한된 Markdown 본문·사용 근거 번호로 받는다. 글 작성용 입력에는 비밀키와 제휴 추적 URL을 보내지 않는다.
- 사용 경험을 꾸민 후기, 근거 없는 수치·성능·효능·할인·최저가 표현을 검사한다. 실제 상품명에 포함된 숫자와 새로 생성한 수치를 구분한다.
- 출처·확인 시각·제휴 고지·구매 링크는 서버 렌더러가 삽입한다. 제휴 고지는 상품 소개 앞에 표시한다.
- 구조·근거·필수 구획·길이 검사를 통과하면 자동 발행 대상으로 기록한다. 이 기록의 이름은 `자동 검사 통과`이며 수동 검토 기록과 구별한다.
- 수정 가능한 작성 오류는 1회 재작성 후 다시 검사한다. 계속 실패하면 작업과 오류를 저장하고 텔레그램으로 알린다.
- 작성과 재작성은 기존 수동 AI 사용과 합산해 `AI_DAILY_LIMIT`를 지킨다. 하루 글 수와 AI 호출 수를 따로 표시한다.
- AI 한도에 도달하면 기존 결과를 보존하고 한도 초기화 후 유효한 발행 슬롯으로 이월한다. 공유 AI 한도의 날짜 기준은 기존 호출 집계와 맞춘다.

자동 글은 상품 하나에 대한 텍스트·목록·표·제휴 링크로 구성한다. 자연어 자동 검사는 등록한 규칙에 대한 검사로 표시한다.

## 7. 서비스별 발행 대기열과 일정

웹의 `자동 운영` 설정에서 쿠팡 하루 편수, 토스 하루 편수, 발행 요일·시간 범위·시간대를 지정한다. 편수는 초기 설정 때 입력한다. 쿠팡 10편·토스 5편은 사용 예시이며 고정 기본값이 아니다. 언어는 한국어, 시간대는 `Asia/Seoul`, 시간 범위는 09:00~21:00을 제안한다.

- 하루 편수는 준비된 링크 대기열에서 발행할 최대 글 수다. 링크가 부족하면 받은 글만 처리하고, 남은 링크는 다음 발행일로 넘긴다.
- 각 서비스의 같은 날짜 내 시간 범위를 편수만큼 균등 분할한다. 예를 들어 3편이면 09:00·13:00·17:00 슬롯이다. 시작 시각은 종료 시각보다 빨라야 하고 슬롯 간격은 최소 1분으로 한다.
- 발행 시각 15분 전부터 5분 전까지 해당 서비스의 `ready` 작업을 접수 순서대로 배정한다. 배정 가능 시간을 지난 미배정 슬롯은 건너뛰고 다음 슬롯을 사용한다. 정보 대기 중인 건이 다른 준비된 건을 막지 않는다.
- 쿠팡·토스 슬롯을 서로 대체하지 않는다. 편수가 0인 서비스는 링크를 대기열에 보관하고 발행을 배정하지 않는다.
- 슬롯의 날짜는 설정 시간대 기준이다. 편수·요일·시간 범위·시간대 변경은 기존 시간대의 다음 날부터 적용하며 적용일을 표시한다.
- 작업이 늦어지면 같은 날짜·발행 범위 안에서 현재부터 5분 이후로 예약한다. 범위를 넘으면 원격 초안 ID와 작성 결과를 보존하고 다음 유효한 슬롯으로 이월한다.
- 슬롯은 사이트·서비스·운영 날짜·번호로 고유하게 식별한다. 동일 슬롯의 재시도는 별도 편수를 소비하지 않는다. 원격 발행 결과가 불명확하면 그 슬롯을 다른 글에 재배정하지 않는다.
- 동일 메시지·동일 제휴 URL의 재전송은 기존 작업을 안내한다. 상품·옵션 ID를 확인할 수 있으면 다른 단축 링크여도 같은 대상을 중복 예약하지 않는다. 서로 다른 단축 링크의 대상을 확인할 수 없을 때까지 같은 상품으로 판단한다고 보장하지 않는다.
- 준비·예약·발행 확인·실패를 서비스별로 집계한다. 예약 성공만으로 발행 완료 수를 올리지 않는다.

자동 운영을 끄면 접수된 링크를 보관하고 새 작성·예약을 중지한다. 이미 예약한 글의 원격 상태 확인과 결과 알림은 계속한다. 한 작업의 일시 오류는 다른 서비스의 준비된 작업 처리를 막지 않는다.

## 8. 저장, 중단 복구와 발행

기존 SQLite `records` 저장 방식에 아래 기록을 추가한다.

- `telegram_cursor`: 봇 ID와 다음 업데이트 오프셋.
- `automation_settings`: 작성 지침·서비스별 편수·일정·활성 여부·버전과 다음 적용 설정.
- `automation_request`: 입력 메시지 식별자, 원문 링크, 서비스, 출처·상품 ID, 근거와 보충 질문 연결, 작업 상태·소유 프로세스·재시도 시각.
- `automation_article`: 상품·작성 설정 스냅샷, 제목·본문·검사 결과·발행 HTML.
- `automation_slot`: 고유한 날짜별 슬롯과 배정된 요청 ID.
- `automation_publication`: 대상 사이트, 요청에서 만든 고유 slug, 원격 글 ID·주소·상태·예약 시각.
- `notification`: 고유 이벤트, 요청 ID, 메시지 내용·전달 상태·시도 수·확인된 Telegram 메시지 ID.

상태 흐름:

`received → inspecting → awaiting_info 또는 ready → composing → checking → draft_sending → scheduling → scheduled → published`

슬롯 배정은 `ready`에서 `composing`으로 넘어갈 때 한다. 부가 상태는 `retry_wait`, `failed`, `uncertain`이다. 입력 보충과 슬롯 이월은 기존 요청을 이어가며 새 요청이나 새 WordPress 글을 만들지 않는다.

DB 트랜잭션으로 작업 소유권과 슬롯을 확보한 뒤 네트워크 요청을 수행한다. 기존 프로세스 소유권 토큰 패턴을 재사용한다. 죽은 프로세스의 읽기·작성 단계는 저장된 결과를 기준으로 복구하고, 외부 쓰기 도중 종료된 작업은 먼저 원격 결과를 조회한다.

### WordPress 전송

1. 자동 검사 통과한 제목·본문·제휴 링크의 스냅샷을 고정한다.
2. **입력 요청 ID**에서 고유 slug를 만든다. 슬롯이 바뀌어도 slug는 바뀌지 않는다.
3. 비공개 초안을 생성하고 반환된 원격 ID를 즉시 저장한다. 기존 raw 재조회 방식을 확장해 제목·본문·고지를 대조한다.
4. 확인된 원격 ID의 글을 예약으로 변경하고 예정 시각·본문을 재조회한다.
5. 실제 상태가 `publish`이고 게시 주소를 확인했을 때만 발행 완료 이벤트를 만든다.

초안 생성 응답을 잃으면 slug로 찾아 내용을 대조한다. 일치하는 결과를 확인하지 못하면 `uncertain`으로 남기고 새 글 생성 요청을 자동 반복하지 않는다. 예약 변경의 응답 유실은 이미 저장한 원격 ID를 조회해 복구한다. 원격 본문이 달라졌다면 해당 작업을 멈추고 오류를 알린다.

예정 시각 이후에도 `future`이면 조회를 계속하고, 15분 이상 지연되면 한 번 알린다. Telegram 전송 실패 때문에 WordPress 요청을 다시 수행하지 않는다.

## 9. Telegram 질문·알림 전달

접수, 정보 보충 요청, 예약 확인, 발행 완료, 작업 오류·결과 불명·지연을 전달한다. 메시지에는 요청 번호와 쿠팡·토스 구분을 넣는다. 발행 완료 시 게시 주소와 해당 서비스의 운영 날짜별 발행 확인 수·설정 편수를 표시한다.

- 상태 변경과 알림 이벤트를 같은 트랜잭션으로 저장하고 별도 전달기가 `sendMessage`를 호출한다.
- 정보 보충은 ForceReply로 답장을 유도한다. 확인된 봇 메시지 ID와 요청 ID를 저장해 응답을 연결한다.
- 응답 유실로 메시지 ID를 저장하지 못한 경우도 고려해 질문에 요청 ID를 표시한다. 그 봇 질문에 대한 답장임을 확인한 뒤, 같은 사용자·채팅의 해당 요청에만 연결한다.
- 고유 이벤트 ID로 알림의 중복 생성을 막는다. Telegram이 메시지를 받고 응답만 유실한 경우 재시도 알림이 중복될 수 있어 요청 번호를 함께 표시한다.
- 429는 `retry_after`, 통신 오류·서버 오류는 최대 3회 지연 재시도를 따른다. 인증·대화 권한 오류는 연결 상태에 표시한다.
- 평문 메시지와 길이 제한을 사용한다. 토큰이 들어간 Telegram 요청 주소·비밀키는 오류 메시지와 로그에 포함하지 않는다.

## 10. 설정 화면과 모듈 경계

자동 운영 화면에는 연결 상태, 작성 지침, 서비스별 발행량·시간 범위, 다음 실행 시각, 정보 대기·준비·예약·발행 목록을 표시한다. 각 작업의 근거·작성 결과·자동 검사·게시 주소·알림 상태를 확인할 수 있게 한다.

활성화에는 Telegram 사용자·채팅 설정, AI·WordPress 설정과 적어도 한 서비스의 양수 편수가 필요하다. 쿠팡·토스 API 키는 활성화 조건에 넣지 않는다. 초기 설정의 `설정됨`과 실제 연결·발행 성공은 별도로 표시한다. `.env.example`과 README에 초기 연결 방법과 Telegram 답장 예시를 추가한다.

| 경계 | 책임 |
| --- | --- |
| Telegram 어댑터·수신기 | API 요청, 사용자·메시지 식별, 접수와 답변 연결, 오프셋 저장 |
| 상품 정보 확인 | 제휴 링크 보존, 제한된 공개 페이지 조회·추출, 근거 스냅샷 |
| 작성 정책 | 템플릿·상황 선택, AI 입력과 출력 검사, 자동 글 렌더링 |
| 자동 실행기 | 슬롯 배정, 상태 전이·재시도·AI 한도·복구 |
| 발행·알림 전달기 | WordPress 결과 대조, 저장된 Telegram 이벤트 전달 |

기존 FastAPI 실행 수명주기에 작업자를 연결하고 기존 수동 편집 기능과 자동 작업의 검토 상태를 구별한다. 웹 경로와 화면은 이 모듈들을 호출하는 연결부로 둔다.

## 11. 검증 기준

1. 쿠팡·토스 API 키가 없는 상태에서 Telegram 링크 접수부터 WordPress 발행 확인·결과 알림까지 모의 외부 HTTP로 검증한다.
2. 조회 성공과 HTTP 403·시간 초과·빈 메타데이터·잘못된 상품 옵션 응답을 검증한다. 실제 확인한 403 사례를 합성 fixture로 재현한다.
3. 원문 제휴 링크의 추적 쿼리가 게시 HTML에서 유지되고, 외부 리다이렉트·내부망 주소·과대 응답을 제한하는지 확인한다.
4. 등록하지 않은 사용자·채팅, 중복 업데이트, 한글·이모지 URL 엔티티, 여러 동시 정보 요청에 대한 답장을 검증한다.
5. 접수 저장과 오프셋 저장 사이의 중단, Telegram 질문 응답 유실과 뒤늦은 보충 답변을 검증한다.
6. 상황별 작성·짧은 글·가격 누락·근거 부족, 1회 재작성과 기존 AI 사용의 공유 일 한도를 검증한다.
7. 쿠팡·토스별 서로 다른 편수, 0편 대기, 시간 분산, 날짜 경계·설정 변경·재시작·슬롯 이월을 검증한다.
8. 중복 접수와 동시 처리, WordPress 생성·예약 응답 유실, 원격 변경에도 새 글을 무조건 재생성하지 않는지 검증한다.
9. Telegram 전송 실패가 발행을 반복하지 않고, 예약 확인과 실제 공개 확인을 구별하는지 검증한다.
10. 웹 초기 설정·대기열·작업 상세를 브라우저에서 검증하고 기존 Python·Node·브라우저 회귀 검증을 수행한다.

테스트에는 합성 계정·상품·링크를 사용한다. 실제 봇·WordPress 연결 결과와 모의 검증 결과를 구분해 보고한다.

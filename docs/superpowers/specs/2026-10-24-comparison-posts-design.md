# 제휴 상품 비교 글 자동 발행 설계

작성일: 2026-10-24
상태: 설계 검토 대기

## 1. 목표와 확정된 결정

텔레그램 한 메시지에 본인 제휴 링크 2~3개를 보내면 상품 비교 글을 작성해 WordPress에 발행한다. 비교가 항상 필요한 것은 아니므로, 확보된 상품만으로 먼저 글을 올리고 나중에 설명이 도착하면 같은 글을 보완한다.

사용자와 확정한 사항:

- 입력은 **한 메시지에 링크 여러 개**다. 링크 하나는 기존 단일 상품 글로 처리한다.
- 일부 상품 정보를 읽지 못해도 **확보된 상품으로 먼저 발행**한다. 비교가 목적이 아니라 소개여도 된다.
- 나중에 설명이 도착하면 **이미 공개된 글도 자동 수정**한다.

설계 원칙:

- 제휴 링크는 보낸 원문을 그대로 쓴다.
- 한 요청은 한 글이다. 상품 수와 관계없이 WordPress 글은 하나만 만든다.
- 공개 글 자동 수정은 **앱이 마지막으로 확인한 본문과 원격 본문이 일치할 때만** 수행한다. 외부에서 수정된 글은 덮어쓰지 않는다.
- 자동 수정은 글의 상태(초안·예약·공개)와 예약 시각을 바꾸지 않는다.

## 2. 입력과 요청 구조

### 링크 접수

- 지원 링크 2~3개를 받으면 요청 하나를 만든다. 4개 이상은 이번 범위에서 거절하고 2~3개로 나눠 보내도록 안내한다.
- 같은 링크의 중복 표기는 하나로 센다.
- 링크별로 서비스(쿠팡·토스), 원문 URL, 상품·옵션 ID, 근거, 상태를 따로 저장한다.
- 기존 단일 상품 요청은 그대로 읽을 수 있어야 한다. 저장 구조는 `products` 목록을 추가하고, 기존 요청은 읽을 때 단일 항목 목록으로 변환한다.
- 링크 하나가 이미 접수된 요청에 속해 있으면 새 요청에서 제외하고 그 사실을 알린다. 남는 링크가 없으면 기존 요청을 안내한다.

### 상품 상태

각 상품은 `ready` 또는 `awaiting_info`다. 요청 전체 상태는 다음과 같다.

| 조건 | 요청 상태 | 동작 |
| --- | --- | --- |
| 모든 상품 ready | `ready` | 바로 작성·발행 |
| 일부 ready, 일부 정보 부족 | `ready` | ready 상품만으로 먼저 발행, 부족한 상품은 `awaiting_info`로 유지 |
| 모든 상품 정보 부족 | `awaiting_info` | 설명 질문만 전송 |
| 발행 후 추가 설명 도착 | `updating` | 같은 글 본문을 다시 작성해 수정 |

요청은 `products`별 상태와 `revision`을 가진다. 상품 설명이 반영되면 해당 상품의 revision만 올라간다.

### 설명 질문

- 정보가 부족한 상품마다 별도 질문을 보낸다. 질문에는 상품 순번(예: `2번 상품`)과 요청 ID를 표시한다.
- 답장은 질문 메시지 ID로 해당 상품에 연결한다. 메시지 ID를 잃어도 본문의 요청 ID와 상품 순번으로 연결한다.
- 한 답장에 여러 상품 설명을 넣지 않는다. 다른 상품 설명은 해당 상품 질문에 따로 답장한다.
- 설명이 도착하면 그 상품만 갱신하고, 같은 글의 재작성 여부를 판단한다.

## 3. 글 유형과 본문

### 유형 선택

| 확보 상태 | 글 유형 |
| --- | --- |
| ready 상품 2~3개, 공통 비교 항목 1개 이상 | 비교 글 |
| ready 상품 1개 | 기존 단일 상품 글(소개·가이드·짧은 글) |
| ready 상품 2개 이상이나 공통 항목 없음 | 상품별 소개를 담은 묶음 글 |

`purpose`(구매 목적)가 설정돼 있고 상품별 사실이 3개 이상이면 구매 가이드 성격을 함께 반영한다. 비교가 부자연스러우면 억지 비교표를 만들지 않는다.

### 비교 항목

- 비교표에는 두 상품 이상에서 **같은 이름으로 확인된 항목**만 넣는다. 예: 가격, 구성 수량, 용량, 색상.
- 한 상품에만 있는 항목은 비교표가 아니라 해당 상품 소개에 쓴다.
- 비교표의 값은 근거에 있는 값만 쓴다. 단위가 다르면 환산하지 않고 각각 표기한다.
- 공통 항목이 하나도 없으면 비교표를 생략한다.

### 본문 구성

1. 제휴 고지(포함된 서비스마다 한 줄)
2. 제목
3. 도입부: 어떤 상품을 어떤 기준으로 골랐는지
4. 비교표(조건 충족 시)
5. 상품별 소개: 이름, 확인한 특징, 이런 경우에 맞음, 구매 전 확인
6. 공통 주의사항
7. 출처와 확인 시점
8. 상품별 제휴 링크

서버가 고지·출처·링크·가격 확인 시점을 삽입하고, AI는 제목·본문·근거 번호만 만든다.

### 분량과 근거

- 비교 글 본문은 최대 3,000자다. 단일 상품 글의 기존 제한은 유지한다.
- 상품별 근거 번호를 `(상품 순번, 근거 번호)`로 구분한다.
- 사용한 근거가 실제 그 상품의 근거인지 검사한다.
- 가격은 상품별로 발행 예정 시점 기준 24시간 이내 값만 쓴다. 만료된 상품의 가격만 제외하고 나머지 상품은 계속 발행한다.
- 상품명에 포함된 숫자와 생성한 수치를 구분하는 기존 검사를 상품별로 적용한다.

### 고지

- 쿠팡과 토스가 섞여 있으면 두 고지를 모두 넣는다.
- 비교표나 상품 소개보다 앞에 표시한다.

## 4. 일정과 편수

- 요청 하나는 한 개의 발행 슬롯을 사용한다. 비교 상품 수만큼 슬롯을 쓰지 않는다.
- 첫 발행 시점에 ready 상품의 서비스가 여럿이면 **포함된 각 서비스의 하루 편수에서 1편씩** 차감한다. 어느 한 서비스라도 당일 남은 편수가 없으면 다음 슬롯으로 넘긴다.
- 첫 발행 뒤 추가된 상품은 이미 발행한 요청의 수정이므로 편수를 추가로 차감하지 않는다.
- 추가 설명은 다음 슬롯을 기다리지 않고, 발행 확인 후 가능한 즉시 같은 글을 수정한다.
- 수정은 새 WordPress 글을 만들지 않는다.

## 5. WordPress 발행과 공개 글 수정

### 최초 발행

기존 단일 상품 발행 절차를 그대로 사용한다.

1. 확보된 상품으로 불변 스냅샷을 만든다.
2. 요청 ID 기반 slug로 비공개 초안을 만든다.
3. 원격 ID를 즉시 저장한다.
4. 예약으로 변경하고 예약 시각·본문을 재조회한다.
5. 실제 공개를 확인한 뒤 완료로 표시한다.

스냅샷에는 상품 목록, 상품별 원문 제휴 링크, 사용한 서비스, 본문, 제목이 들어간다.

### 추가 설명 후 수정

수정은 `update_snapshot` 한 곳에서 처리한다.

1. 원격 글을 읽어 현재 제목·본문이 **직전 스냅샷과 일치**하는지 확인한다.
2. 일치하면 새 본문으로 같은 글 ID를 갱신한다.
3. 다시 읽어 새 스냅샷과 일치하는지 확인한다.
4. 글 상태(초안·예약·공개)와 예약 시각은 바꾸지 않는다.
5. 공개 글이면 수정 후 게시 주소와 상태를 재확인한다.

외부에서 본문이 수정됐거나, 원격 상태가 예상과 다르거나, 게시 주소를 확인할 수 없으면 **덮어쓰지 않고** 요청을 `update_blocked`로 남기고 텔레그램으로 알린다. 사용자는 WordPress에서 직접 확인한 뒤 웹 화면에서 수정 재시도를 선택할 수 있다.

### 응답 유실

- 수정 요청의 응답을 잃으면 원격 글을 다시 읽는다. 새 스냅샷과 일치하면 완료, 직전 스냅샷과 일치하면 재시도 가능, 둘 다 아니면 `update_blocked`다.
- 공개 글 수정 중 앱이 종료되면 다음 시작 시 같은 절차로 판정한다. 새 글을 만들지 않는다.

## 6. 저장 구조

기존 `records` 테이블을 그대로 쓴다.

- `automation_request`: `products` 목록, 상품별 상태·근거·제휴 URL·질문 메시지, `revision`, `update_state`, `update_error`
- `automation_article`: 현재 스냅샷, 사용한 글 유형, 상품별 근거
- `automation_publication`: 원격 ID, 직전 스냅샷, 수정 시각, 마지막 확인 시각
- `notice`: 상품별 질문과 수정 결과 알림

기존 단일 상품 레코드는 읽기 시 `products` 한 항목으로 변환한다. 저장할 때는 새 구조로 쓴다. 데이터 마이그레이션은 앱 시작 시 일괄 변환하지 않고, 해당 요청을 읽거나 갱신할 때 변환한다.

## 7. 화면

자동 운영 요청 상세에 다음을 추가한다.

- 상품별 이름, 상태, 제휴 링크, 근거, 가격 확인 시점
- 어떤 상품이 설명 대기인지
- 비교표와 본문 미리보기
- 수정 이력과 마지막 원격 확인 시각
- `update_blocked`일 때 사유와 **수정 재시도** 버튼, WordPress 관리자 링크

기존 `원격 상태 조회` 버튼은 그대로 두고, 수정 재시도는 별도 버튼으로 분리한다.

## 8. 실패 처리

- 상품 조회 일시 오류: 기존처럼 지연 재시도 후 설명 요청으로 전환한다.
- AI 한도 소진: 요청을 유지하고 다음 UTC 날짜 슬롯에서 재개한다. 추가 설명 수정도 같은 한도를 쓴다.
- AI 생성·검사 실패: 최대 3회 시도 후 `failed`. 실패한 요청은 같은 링크를 다시 보내 재접수할 수 있다.
- WordPress 수정 실패: `update_blocked`로 남기고 자동 재시도하지 않는다. 외부 수정 가능성을 배제할 수 없기 때문이다.
- 알림 실패: 글 발행·수정을 반복하지 않는다.

## 9. 검증 기준

1. 한 메시지의 링크 2개·3개가 요청 하나와 글 하나로 처리된다.
2. 일부 상품이 403이어도 ready 상품만으로 발행되고, 부족한 상품 질문이 따로 전송된다.
3. 역순 답장과 질문 응답 유실에서도 설명이 해당 상품에만 연결된다.
4. 공개 후 추가 설명이 도착하면 같은 글 ID가 수정되고 새 글이 생기지 않는다.
5. 외부에서 본문을 수정한 경우 자동 수정이 차단되고 `update_blocked`로 표시된다.
6. 수정 응답 유실·앱 재시작에서 새 글 생성 없이 상태가 판정된다.
7. 비교표에는 공통 항목만 들어가고, 공통 항목이 없으면 생략된다.
8. 혼합 서비스 글은 고지 두 개와 각 제휴 링크를 모두 포함한다.
9. 편수는 첫 발행에서만 차감되고, 수정은 편수를 추가로 쓰지 않는다.
10. 기존 단일 상품 요청과 수동 기능이 그대로 동작한다.
11. 모의 Telegram·AI·WordPress로 전체 흐름을 검증하고, 실제 계정 검증은 별도로 보고한다.

## 10. 이번 범위에서 제외

- 이미지 업로드와 본문 이미지 삽입(다음 단계)
- 4개 이상 상품 비교
- 상품 정보 API 자동 조회
- 공개 글의 예약 시각·상태 변경
- 외부에서 수정된 글의 자동 병합

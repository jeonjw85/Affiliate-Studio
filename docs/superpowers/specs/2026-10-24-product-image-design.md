# 상품 대표 이미지와 AI 본문 이미지 설계

작성일: 2026-10-24
상태: 설계 검토 대기

## 1. 목표와 확정된 결정

자동 운영 글이 상품 페이지의 대표 이미지를 가져와 WordPress 대표 이미지로 한 장 지정하고, 본문에는 AI가 만든 삽화 이미지를 한 장 넣는다.

사용자와 확정한 사항:

- **대표 이미지**는 상품 페이지에서 자동 추출한 이미지 1장이다.
- **본문 이미지**는 AI가 생성한 삽화 1장을 본문 상단에 넣는다. 상품 실물 사진처럼 보이게 만들지 않는다.
- 상품별 이미지는 넣지 않는다.
- 상품 이미지를 구하지 못해도 글은 발행한다. 본문 이미지는 상품 이미지와 독립이며, 생성에 실패하면 본문 이미지 없이 발행한다.
- 알림과 화면에 대표·본문 이미지의 포함 여부와 사유를 표시한다.

현재 앱은 `AI_MODE=api`(OpenAI 호환)를 전제로 하지만 `AI_BASE_URL`·`AI_MODEL`·`AI_API_KEY`가 비어 있어 채팅 AI도 아직 연결되지 않은 상태다. 이미지 생성은 같은 계열의 **OpenAI 호환 이미지 API**를 쓰고, 다음 환경변수로 별도 설정한다.

```dotenv
IMAGE_MODE=api                 # api 또는 local
IMAGE_BASE_URL=                # 예: https://api.openai.com/v1
IMAGE_MODEL=                   # 예: gpt-image-1
IMAGE_API_KEY=                 # 이미지 서비스 키
IMAGE_DAILY_LIMIT=3
```

`IMAGE_MODE`가 비어 있으면 이미지 생성은 비활성으로 두고, 상품 대표 이미지만 사용한다.

설계 원칙:

- 페이지 조회는 기존 `studio/product_info.py`의 제한된 HTTPS·DNS 고정·용량 제한을 그대로 쓴다. 이미지 다운로드에도 같은 제한을 적용한다.
- 이미지 파일은 사용자가 보낸 링크의 페이지에서만 가져오고, HTML 안의 임의 URL을 실행 대상으로 삼지 않는다.
- 원본을 자르거나 합성·번역하지 않는다. WordPress가 만드는 크기 변형만 허용한다.
- 이미지 업로드는 글 생성과 분리한다. 업로드 실패가 글 발행을 막지 않는다.
- 같은 요청을 재시도해도 미디어가 중복 생성되지 않는다.

## 2. 이미지 추출

### 후보 선택

페이지 HTML에서 다음 순서로 하나를 고른다.

1. JSON-LD `Product.image` (문자열 또는 `{url}`)
2. `og:image`
3. `twitter:image`

- `https` 절대 주소만 허용한다.
- 쿠팡·토스의 이미지 호스트만 허용한다. 허용 목록은 `coupangcdn.com` 계열과 토스 이미지 호스트로 시작하고, 실제 링크 조사에서 확인한 호스트만 추가한다.
- 데이터 URI, 상대 경로, `javascript:`·`file:` 등은 거부한다.
- `Content-Type`이 `image/jpeg`, `image/png`, `image/webp` 중 하나여야 한다.
- 최대 8MiB, 최소 200×200픽셀. 픽셀 크기는 파일 헤더에서만 확인하고 전체 디코딩은 하지 않는다.
- 페이지 조회가 차단(403)되거나 후보가 없으면 이미지 없음으로 처리한다.

### 저장

- 다운로드한 바이트를 데이터 폴더의 `media/` 아래에 `<request_id>-<sha256 앞 16자>.<ext>`로 저장한다.
- 같은 파일이 이미 있으면 다시 쓰지 않는다. 원본 URL·해시·크기·Content-Type을 `automation_media` 레코드에 남긴다.
- 파일 저장 후 DB 기록을 남긴다. 파일만 남고 기록이 없으면 다음 실행에서 다시 사용한다.
- 요청 삭제·취소 기능은 이번 범위에 없으므로 파일은 보관한다. 디스크 사용량을 화면에 표시한다.

## 3. WordPress 업로드

### 절차

1. `POST /wp-json/wp/v2/media`에 `Content-Disposition: attachment; filename="..."`, `Content-Type`과 함께 바이트를 보낸다.
2. 응답의 `id`, `source_url`을 검증해 `automation_media`에 저장한다.
3. 글 생성·수정 시 `featured_media`에 그 ID를 넣는다.
4. 업로드 응답을 잃으면 미디어 목록을 조회해 파일명·해시가 같은 항목을 찾는다. 찾으면 재사용하고, 찾지 못하면 새로 만들지 않고 이미지 없이 발행한다.

### 중복 방지

- 요청 ID와 이미지 해시로 업로드 기록을 먼저 확인한다.
- 같은 요청의 글이 재작성·보완되어도 기존 `featured_media` ID를 재사용한다.
- 글 수정 시 `featured_media`가 이미 같은 값이면 다시 보내지 않는다.

### 실패 처리

- 다운로드 실패, 허용하지 않는 형식, 업로드 거부, 응답 유실 후 확인 실패: **이미지 없이 발행**.
- 알림과 화면에 `대표 이미지 없이 발행` 사유를 남긴다.
- 업로드 자체는 재시도하지 않는다. 글 발행을 반복하지 않기 위해서다.
- WordPress 대표 이미지 지정이 실패하면 글은 그대로 두고 이미지 없이 발행된 상태로 기록한다.
- 본문 이미지 업로드가 실패하면 대표 이미지·본문 텍스트만으로 발행한다.

## 3-1. AI 본문 이미지

### 생성

- 글 작성이 끝나면 같은 근거에서 이미지 프롬프트를 만든다. 프롬프트에는 상품명·카테고리·대상 독자만 쓰고, 제휴 URL·가격·개인정보·실제 인물은 넣지 않는다.
- 프롬프트는 `OpenAI 호환 POST /images/generations`로 보낸다. 요청은 `model`, `prompt`, `size`(1024x1024), `n=1`, `response_format=b64_json`을 쓴다.
- 응답은 `b64_json`만 허용한다. URL 응답은 외부 호스트로 나가므로 받지 않는다.
- 결과는 JPEG/PNG/WebP, 최대 8MiB, 최소 512×512로 검증한다.
- 같은 요청에는 이미지 1장만 만든다. 글이 보완되어도 기존 본문 이미지를 유지한다.
- 생성 결과에는 `AI 생성 이미지` 표시를 붙인다. `alt`와 이미지 캡션에 이 사실을 넣는다.

### 안전 규칙

- 실제 상품 사진처럼 보이거나 상품의 성능·효능을 암시하는 이미지를 만들지 않는다. 프롬프트에 `제품 실물 사진 아님, 설명용 삽화`를 명시한다.
- 사람 얼굴·로고·상표·텍스트를 넣지 않는다. 생성 결과에 텍스트가 보이면 사용하지 않는다.
- 이미지 생성 실패·한도 소진·형식 오류는 글 발행을 막지 않는다. 본문 이미지 없이 발행하고 사유를 남긴다.
- 이미지 생성 호출은 기존 `AI_DAILY_LIMIT`와 별도인 `IMAGE_DAILY_LIMIT`로 제한한다. 실패 시도도 포함해 UTC 날짜 기준으로 센다.
- 이미지 생성은 발행을 반복시키지 않는다. 같은 요청의 재시도는 저장된 결과를 재사용한다.

### 본문 삽입

- 본문 최상단, 제목 다음에 `<figure><img ...><figcaption>AI 생성 이미지 · 설명용 삽화</figcaption></figure>`를 넣는다.
- 이미지는 WordPress 미디어로 업로드한 뒤 그 URL을 쓴다. 외부 원본 URL을 직접 핫링크하지 않는다.
- 대표 이미지와 본문 이미지가 서로 달라도 된다. 대표 이미지는 상품 페이지, 본문은 AI 생성물이다.

## 4. 글과의 연결

- 스냅샷에 `featured_media: int|null`, `body_media: int|null`, `body_image_html: str`을 추가한다.
- `ensure_draft`는 글 생성 전에 미디어를 준비하고, 준비된 ID를 payload에 넣는다.
- `update_snapshot`은 기존 `featured_media`를 유지한다. 새 이미지가 준비된 경우에만 교체한다.
- 기존 스냅샷에는 이 필드가 없으므로 읽을 때 `None`으로 처리한다.
- 글 검증(`verify_snapshot`)은 제목·본문·고지·제휴 링크를 그대로 확인한다. `featured_media`는 WordPress 응답에 있으면 비교하고, 없으면 검증 대상에서 제외한다.

## 5. 저장 구조

- `automation_media`: `{id, request_id, kind, source_url, host, prompt, content_type, bytes, sha256, width, height, local_path, remote_id, remote_url, state, error, created_at}`
- `kind`: `featured`(상품 페이지 이미지) 또는 `body`(AI 생성 이미지)
- `state`: `fetched`, `generated`, `uploaded`, `unavailable`, `upload_uncertain`
- 이미지 생성 사용량: 기존 `operation` 기록에 `type='image'`, `scope='automation'`으로 남긴다.
- 기존 `records` 테이블을 그대로 쓴다. ID는 `record_id('media', request_id)`.

## 6. 화면과 알림

- 요청 상세에 대표 이미지와 본문 이미지의 상태(확인함·생성함·없음·업로드 완료)와 썸네일을 표시한다.
- 썸네일은 앱이 저장한 파일만 표시하고 원본 외부 URL을 직접 불러오지 않는다.
- 발행 알림에 `대표 이미지 포함/없음`, `본문 이미지 포함/없음`을 표시하고 사유가 있으면 함께 적는다.
- 이미지 출처 URL은 화면에 표시하되 링크로 만들지 않는다.
- 디스크 사용량(파일 수·바이트)을 자동 운영 화면에 표시한다.

## 7. 보안과 저작권 경계

- 이미지 요청에도 기존 공개 IP 고정·리다이렉트 제한·20초 제한을 적용한다.
- 이미지 URL의 호스트가 허용 목록에 없으면 요청하지 않는다.
- 파일명은 서버가 만든 해시만 쓴다. 원본 파일명·경로를 저장 경로로 쓰지 않는다.
- 이미지 저작권·사용 허용 여부는 앱이 보증하지 않는다. 사용자가 링크를 보낸 상품 페이지의 이미지를 대표 이미지로 쓰는 범위이며, 게시 전 확인 책임은 사용자에게 있다. README와 시작하기에 이 경계를 적는다.
- 이미지에 얼굴·개인정보가 포함될 수 있으므로 자동 검열을 하지 않는다는 점을 명시한다.

## 8. 검증 기준

1. JSON-LD·OG·Twitter 순서로 대표 이미지를 하나만 고른다.
2. 허용하지 않는 호스트·형식·용량·작은 이미지·데이터 URI는 요청하지 않고 `unavailable`이 된다.
3. 페이지가 403이면 이미지 없이 글이 발행되고 알림에 표시된다.
4. 다운로드 이미지는 `media/`에 해시 파일명으로 저장되고, 같은 요청 재실행에서 중복 저장·중복 업로드가 없다.
5. 업로드 성공 시 글의 `featured_media`가 그 ID로 생성된다.
6. 업로드 응답 유실 시 미디어 목록 조회로 재사용하거나, 확인 불가면 이미지 없이 발행한다.
7. 글 보완 시 기존 대표 이미지가 유지되고 새 업로드가 생기지 않는다.
8. 기존 이미지 없는 글·수동 기능·비교 글 흐름이 그대로 동작한다.
9. 화면·알림이 이미지 포함 여부와 사유를 표시하고, 썸네일은 로컬 파일만 쓴다.
10. 이미지 생성은 OpenAI 호환 응답(b64_json)만 받고, URL 응답·허용 외 형식·과대 용량은 거부한다.
11. 생성 실패·한도 소진·본문 이미지 없음에서도 글이 발행되고 사유가 표시된다.
12. 글 보완 시 기존 본문 이미지가 유지되고 새 생성이 생기지 않는다.
13. 모의 페이지·AI 이미지·WordPress로 전체 흐름을 검증하고 실제 계정 검증은 별도로 보고한다.
